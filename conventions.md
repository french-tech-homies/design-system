# MD3 kit — conventions

How components in this kit are written, so new ones match and tools (a design
agent, a registry, a linter) can rely on the same shape. Read alongside
`README.md` (install/use) and `tokens/` (the values).

## Source of truth

- **The project's `DESIGN.md`**, at its root, is where colour, type, corner,
  elevation, motion and state opacity values come from, and the only file to
  edit: the first three in its front matter, the rest in the `:root` rule of
  its body's `## Reference CSS` block, which also says how dark is switched.
  `npm run theme:generate` turns it into the two files below (the contract is
  `skills/ds-theme/design-md.md`, which travels with the install). To _read_ the design —
  every role of both schemes, the whole type scale, every value of the block —
  open `tokens/DESIGN.resolved.md`, the complete DESIGN.md the kit writes
  back; never edit it.
- **Color:** `tokens/theme.css` — the 49 Material roles as finished colors,
  `--md-sys-color-<role>: hsl(…)`, light on `:root`, dark on `.dark` or under
  `prefers-color-scheme: dark`, as the project's `DESIGN.md` chooses.
  Generated; never hand-edit.
- **Type, shape, elevation, motion:** `tokens/theme.v4.css` (`@theme inline`).
  Its type, corner, typeface, elevation, easing, duration and state opacity
  values are set from `DESIGN.md`; the mapping to Tailwind is written there.
- **Resolved values:** `tokens/resolved.json` — generated by
  `npm run theme:resolve`; hex per role in both schemes, type scale in px,
  shape radii, elevation shadows, easing, durations, state-layer opacities.
  Never hand-edit; regenerate after any token change.
- shadcn's variable names (`--card`, `--muted`, `--ring`…) exist only in
  `tokens/bridge-shadcn.css` and only for the shadcn component family.

## Styling idiom: Tailwind utilities named after Material roles

Write colors as **role utilities**, never palette or hex classes:

    bg-primary text-on-primary                 filled
    bg-secondary-container text-on-secondary-container   tonal
    bg-surface-container-low text-on-surface   elevated surfaces
    border-outline-variant                     hairlines
    text-on-surface-variant                    secondary text

Pairing rule: a `bg-<role>` always carries `text-on-<role>` (or
`text-on-<role>-container`). Surfaces come in tiers — `surface-container-
{lowest,low,,high,highest}` — pick the tier, do not add borders to fake depth.

**Content color is inherited.** The pair on the container is what colors its
subtree, so nothing inside restates it — the `Display/Headline/Title/Body/
Label` primitives assert no color at all, and a child that hard-codes one is a
bug (it was: #124). The scheme's default is the ambient `color:
var(--md-sys-color-on-surface)` declared on `:root` and `.dark` in
`tokens/theme.css` — the one thing in that file that paints rather than
defines — which is why a `bg-surface-container-*` tier needs no `text-on-
surface` to read correctly, and why an app that wants a different default sets
`color` on `<body>`. State a role only where inheritance is not what you want:
`<Body colorRole="on-surface-variant">` for supporting text, `<Label
colorRole="primary">` for an accent on a neutral surface. A `className` still
wins over `colorRole` — which is named that way, and not `color`, because
`color` is a real (deprecated) HTML attribute and these primitives are
prop-forwarding targets. `stories/foundations/Typography.stories.tsx`'s
`OnColoredContainers` renders every role on every colored container so axe
keeps this honest under both presets.

Other scales, one utility family each:

- Type: `text-display-large` … `text-label-small` (15 roles; includes size,
  line-height, tracking, weight), on two faces — `font-brand` for
  display/headline/title, `font-plain` for body/label, both defaulting to
  `--font-inter`. Each role has a family of its own, `font-<role>`
  (`font-title-small`): the one a project's `DESIGN.md` writes on the role,
  else the role's face. Prefer the `Display/Headline/Title/Body/Label`
  primitives over raw classes: they add the family, which a `text-*` class
  alone does not carry. **A `text-<role>` written in a kit file is written
  with its `font-<role>`**, under the same variant where the role is under
  one (`peer-focus:text-body-small peer-focus:font-body-small`), so a role is
  one family in a page, in a primitive and in a table's header alike. The weight is the role's, in the `text-*` utility
  (`--md-sys-typescale-<role>-weight`): a component writes no weight class
  beside a role, or a project's `DESIGN.md` could not move it. The one
  written weight Material asks for is the prominent weight of an active
  navigation label (`font-bold` in `BottomNavigation` and
  `NavigationDrawer`).
- Shape: `rounded-shape-{extra-small,small,medium,large,large-increased,extra-large,full}`
  (4/8/12/16/20/28px/pill). Components own their shape role: buttons `full`,
  chips `small`, cards `medium`, dialogs `extra-large`.
- Elevation: `shadow-elevation-1` … `shadow-elevation-5`.
- Motion: `duration-short-1 … duration-long-4`, `ease-standard*`,
  `ease-emphasized*`. Enter with `emphasized-decelerate`, exit with
  `emphasized-accelerate`/`short-4`.
- State: `state-opacity-{hover,focus,pressed,dragged}` (8/10/10/16 %, read from
  `--md-sys-state-*`); `opacity-38` disabled content, `/12` disabled
  containers. Never Tailwind's numeric `opacity-8` for a state layer — it
  compiles to a literal, and a theme cannot move it.

## Interaction states

Every pressable renders a **state layer**: an absolutely positioned overlay in
the content color whose opacity follows the state. Two implementations, same
numbers:

- Render-prop driven: `primitives/StateLayer.tsx` with `isHovered`,
  `isFocusVisible`, `isPressed`, `isDragged`.
- CSS driven, for children of a React Aria element carrying `group/<name>`:
  `group-hover/<name>:state-opacity-hover
group-data-focus-visible/<name>:state-opacity-focus
group-data-pressed/<name>:state-opacity-pressed
group-data-dragging/<name>:state-opacity-dragged`.

Focus keys on **focus-visible**, never plain focus. The focus indicator is
`focusRing` from `utils.ts` (3px `ring` = secondary, 2px offset); extend it,
do not invent another. It is an outline whose gap is not painted, so it shows
the ground the control stands on. A part that fills a box that clips (a
table's cell) draws it inside with `-outline-offset-2`.

Variants are Tailwind's own (`hover:`, `focus-visible:`, `disabled:`) plus the
bare data-attribute variants React Aria emits (`data-pressed:`,
`data-selected:`, `data-entering:`, `data-exiting:`, `data-[placement=top]:`).
No Tailwind plugin.

## Theming layers — where a style is allowed to live

Everything in the kit sits in exactly one of three layers, and a consuming app
is invited to touch only the first two:

- **tokens** — `tokens/theme.css`, `tokens/theme.v4.css`,
  `tokens/bridge-shadcn.css`, plus the per-component escape-hatch variables a
  component reads from its ancestors (`--md3-field-notch`). An app may replace
  any of them, by generating its own from its `DESIGN.md` into a folder of its
  own and importing those. No update reaches that folder: components name
  roles and scales, never values, and no registry item writes a palette value
  — the `tokens` item carries the kit's files, `theme` / `base` write only
  the shadcn bridge's references, and `ds` writes nothing into an app's CSS.
- **style modules** — `components/<x>-styles.ts` exporting a `tv` object named
  `<x>Styles`. `components/field-styles.ts` → `fieldStyles` is the precedent
  and the naming contract. These are the only component-level files whose
  names an update keeps for an app that edited them, so their **slot and
  variant names are API**: renaming or
  removing one is a breaking change, changing what a slot contains is not.
- **behaviour** — the React Aria wiring, `utils.ts`, `render-props.ts`,
  `icons.tsx`. An update replaces them and promises no name in them. An app's
  edit of one is allowed, priced and rarely needed; an app that needs
  different behaviour is better served by its own component on React Aria
  beside the kit.

**When a `tv` becomes a style module:** either more than one component renders
from it, or its anatomy is the product's identity rather than the component's
function. Otherwise keep it as `const styles = tv({…})` in the component file.
A component that shares an anatomy with an existing module must render from
that module — add a variant to it rather than a second copy (`fieldStyles`'
`kind` variant is how one container serves typed, composite and trigger
fields). Whatever the layer, `npm run registry:build` must keep generating it:
no hand-maintained registry items, ever.

**What ships to a project's agent** is `skills/`: `ds-theme` (with the
DESIGN.md contract), `ds-build` and `ds-spec`, landed in the project's
`.claude/skills/` by the one install. A skill's text is the kit's, read in any
project: it names kit files as `<kit>/…`, only files the install brings, and
nothing of this repository. Its frontmatter is strict YAML (quote a
description that holds a colon and a space), with the folder's name as
`name`. `npm run registry:check-install` enforces all four. This file and `README.md` are the maintainer's and are in
no item: a rule a project's agent needs goes in a skill.

The three layers, the update mechanism and what a themed app pays at update
time: `README.md`, "Retheming — the three layers". What a project may change,
and its price, is one rule stated once: `skills/ds-build/SKILL.md`, "What a project may change". What the kit is, and which
components are its own: `README.md`, "What this kit is".

## Component anatomy

- Behavior comes from `react-aria-components`; the kit adds only styling and
  Material anatomy. Presentational pieces (`Card`, `ListItem`, `MenuItem`,
  `Typography`, `EmptyState`, `DialogContent`) are server-safe — no
  `react-aria-components` import, no `"use client"`.
- Styles are one `tv()` (from `utils.ts`, bound to the MD3 tailwind-merge
  config) per component — or a shared style module, per the layer rule above —
  with **slots** for anatomy (`base`, `stateLayer`,
  `icon`, `label`, …) and **variants** named after Material's own
  (`filled | tonal | outlined | text | elevated | fab`, `assist | filter |
input`, `plain | rich`). Boolean state variants are `isDisabled`,
  `isSelected`, `isDragged`.
- Every root element carries `data-slot="<component>"` (`button`, `card`,
  `chip`, `modal`, `menu-item`…), plus `data-variant` / `data-size` when the
  component has them; overlays carry `data-slot="state-layer"`. Target parts by
  slot, never by class.
- A component whose parts a caller may need to reach takes `classNames`, an
  object keyed by its `tv` slot names, the root left out (the root keeps
  `className`). Each such part carries `data-slot="<component>-<part>"`
  (`tooltip-content`, `card-headline`), and the doc comment lists the parts.
  `Tooltip` and `Card` are the precedent. A key of `classNames` is a prop:
  renaming one is a break, listed in the changelog. What a project may do with
  it is the skill's to say (`skills/ds-build/SKILL.md`, "What a project may
  change"), not this file's.
- Class merging goes through `cn` / `composeTailwindRenderProps` so caller
  `className` overrides win over the kit's own utilities.
- Icons: any component taking `{ size, className }` (lucide, custom SVG).
  `renderIcon()` accepts a component or an element. Default sizes: 18 in
  buttons/chips, 24 in FABs and lists.
- Server vs client: anything backed by React Aria is `"use client"`;
  `utils.ts` must stay free of `react-aria-components` (see `render-props.ts`).

## Spec review (before a component is "done")

The contract is the published Material 3 site, not any implementation of it
(material-web is in maintenance mode and its token files lag the spec). For
each component read the four pages —
`https://m3.material.io/components/<component>/{overview,specs,guidelines,accessibility}`
— and check the whole implementation against them: anatomy and measurements
(container, padding, icon sizes, state-layer and 48dp touch target), color
roles per state, behaviours in _guidelines_ (what floats, swaps, grows,
appears), and _accessibility_ (labels, roles, live regions, keyboard). Read
them with the `ds-spec` skill (`skills/ds-spec/`, `npm run md3 -- page
<component> guidelines`, `… tokens <component>`): it fetches the site's own
JSON, no browser needed, cached per site version. Link the pages from the
component's doc comment and record any deliberate deviation there.
`spec-version.json` records the site version the kit was last audited
against; `npm run md3 -- check` reports when the spec moved.

When it moves, re-audit before bumping `carbonVersion`. Run `npm run md3 --
refresh` once, then take two dates per audited component from the provenance
lines: the page's `updated` date (`md3 page <component> overview` — one date
covers the four tabs) and the token table's revision (`md3 tokens
<component>`). A component is unchanged only when both are strictly earlier
than its date in `audited`; a same-day date counts as changed, since the
audit may have come before that day's edit. Read every other component again
in full, the four tabs and the tokens, and set its date to the day it was
read. An unchanged component keeps its date: a date is bumped only for what
was really read. `carbonVersion` moves last, once the whole list is covered
against one and the same site version.

The behaviour side is React Aria Components, and it moves monthly: keep
`react-aria-components` on the current release whenever you touch a
component (check `npm view react-aria-components version` and the release
notes at `https://react-aria.adobe.com/releases/v<major>-<minor>-0.md`).
Read its docs as markdown — any page plus `.md`, e.g.
`https://react-aria.adobe.com/ComboBox.md` — or through this repository's
`react-aria` skill (`.claude/skills/react-aria/`: Adobe's, never edited here,
refreshed only by `npx skills update`). Compose the React Aria primitives the docs show
(`ComboBox` + `ComboBoxValue` + `TagGroup`, `ToggleButtonGroup`, …) and let
MD3 dictate anatomy, tokens and behaviour on top.

## Build and preview

    npm run storybook          # catalog: MD3/<Category>/<Component>
    npm run build-storybook    # what CI runs
    npm run theme:resolve      # refresh tokens/resolved.json
    npm run test-storybook   # every story, rendered + axe

Stories live in `stories/`, grouped by Material's taxonomy —
Foundations, Actions, Communication, Containment, Navigation, Selection. Each
component story shows at least three visually distinct variants; foundations
pages render straight from `resolved.json`.

## The quality bar — what a new component must ship

Before any of it, a new component is Material's or it is not the kit's. Its
doc comment cites its page of m3.material.io; or the repository's owner adds
it to the closed group in `README.md`, "What this kit is", and its doc comment
says "Material 3 does not describe this component." `npm run
registry:check-install` (`scripts/check-components.mjs`) refuses a component
file that does neither, and a list and files that differ.

Then four things, and CI (`.github/workflows/checks.yml`) enforces all
of them:

1. **A story** in `stories/<Category>/<Component>.stories.tsx`, titled
   `MD3/<Category>/<Component>`, showing at least three visually distinct
   variants. This is the visual catalog: each of these is looked at as a
   picture.
2. **An interaction test wherever there is behaviour.** If the component
   responds to a keystroke, a press or a selection, it needs a story with a
   `play` function proving it. Those live in `stories/interactions/`, titled
   `MD3/Interactions/<Group>`, deliberately apart from the catalog — a story
   whose point is a keystroke has nothing to show, and mixing them would put
   noise among the pictures. Name each one after what it proves
   (`SelectEscapeCloses`, not `Test3`), and **assert the keyboard path**: a
   control that only works with a mouse is broken. Portalled surfaces
   (popovers, menus, modals) are not inside `canvasElement` — reach them with
   `screen`, not `within(canvasElement)`.
3. **axe clean.** Every story is checked, under both presets. A violation
   fails the build.
4. **Any exception written down where it is made.** An accepted violation is a
   per-story `parameters.a11y.config.rules` entry with a comment saying why —
   either that the rule is wrong here (MD3's disabled content is
   `on-surface/38`, which WCAG 1.4.3 exempts as an inactive component) or that
   it is a real defect with an issue number. Never a blanket disable in
   `.storybook/preview.ts`. An unexplained suppression is worse than no check.

Both projects run from one Vitest config (`vitest.config.ts`): `material` uses
the shipped tokens, `editorial` injects `__MD3_PRESET__` so the whole catalog
renders under `tokens/preset-editorial.css`. Run one with
`npm run test-storybook -- --project=editorial`.

## Not in the kit (yet)

Search bar, date/time pickers: Material 3 describes them.
When adding one: follow the anatomy above, name variants after Material, cite
its page in the doc comment, clear the
quality bar (story, interaction test, axe under both presets), and keep
`README.md`'s component table current. A component Material 3 does not
describe is not on this list: it joins the kit only through the group in
`README.md`, "What this kit is".
